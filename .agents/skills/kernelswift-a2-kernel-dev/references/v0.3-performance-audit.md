# KernelSwift skill v0.3 — Huawei performance audit

## Scope

This note records the evidence that motivated the v0.3 workflow changes. It is
not a benchmark report for a promoted submission.

## Observed remote state

- Host: `liteserver-4db9`, eight healthy Ascend `910B3` devices, CANN 8.5.2.
- Checkout: `/home/tinglin/wksp/KernelSwift` on `main`, with an uncommitted
  v0.1 prototype and an untracked v0.2 prototype/build output.
- No checked-in v0.2 performance report or raw profiler CSV/JSON was present.

## Measured result

The remote agent ran:

```bash
source .venv/bin/activate
source "${ASCEND_HOME_PATH}/set_env.sh"
cmake -S optimized/sparse_attention_v0_2 \
      -B optimized/sparse_attention_v0_2/build
cmake --build optimized/sparse_attention_v0_2/build -j4
python benchmarks/ks/auto_bench.py \
  --v0_file baseline/sparse_attention.py \
  --v1_file optimized/sparse_attention_v0_2/sparse_attention_v0_2.py \
  --atol 1e-2 --rtol 1e-2 --warmup 5 --repeat 20
```

Observed output:

```text
[100%] Built target sparse_attention_v0_2_ops
PASS accuracy; v0=8.049227 ms, v1=99.988423 ms, speedup=0.081x
Summary: 1 passed, 0 failed, 1 total.
```

An independent bounded repeat on the same host, using the same accuracy,
warmup, and repeat settings, also passed correctness and reported:

```text
PASS accuracy; v0=8.058882 ms, v1=99.889826 ms, speedup=0.081x
Summary: 1 passed, 0 failed, 1 total.
```

This repeat confirms the direction and approximate magnitude of the
regression. It is not a three-fresh-process final performance certification;
that more expensive gate is unnecessary for rejecting an already much-slower
candidate.

The attempted vectorized design compiled but was rejected after a reported
`max_abs_diff` of approximately `3.9` and `mean_abs_diff` of approximately
`0.29`. The retained v0.2 kernel was a correctness-passing copy of the scalar
vector implementation. Classify this result as `correctness-only`
`performance-regressed`, not as an optimized release.

## Root-cause hypotheses to test next

1. The scalar kernel performs per-head, per-index dot products and repeated
   reductions; this is the dominant algorithmic bottleneck for `H=64,D=128,K=16`.
2. The vectorized attempt likely violated Ascend C local-tensor layout or
   reduction synchronization semantics; re-derive the tile contract from the
   A2 API references and validate intermediate tensors before integrating it.
3. The Python wrapper adds explicit `torch.npu.synchronize()` calls around a
   raw launch. Measure this overhead separately; do not assume it explains the
   ~12.4× regression without profiler evidence.
4. A dense `QK`/`PV` Cube path needs an AIC/AIV protocol and artifact-backed
   timing before promotion.

## v0.3 policy response

- Require three fresh-process stable measurements and a repeatable improvement
  before promotion.
- Require raw profiler artifacts and a source/binary/adapter audit.
- Bound Cube/Mmad exploration and preserve a known-good correctness artifact.
- Label failed stages explicitly instead of incrementing a version number.
